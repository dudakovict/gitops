# docqa

Upload large PDFs and ask questions about their contents. Answers are generated by Gemini
from passages retrieved out of the document and cite page numbers.

Built as a production-shaped reference for running an LLM application on OpenShift with
GitOps: Jenkins builds and scans, Argo CD deploys, Istio secures service-to-service traffic
with mTLS, and OpenTelemetry carries traces and metrics.

## How it works

```
browser ──HTTPS──> OpenShift Router ──> Istio ingress gateway (Envoy)
                                             │ mTLS
                                             ▼
                                        docqa-api (FastAPI, LangChain)
                                        │ upload: store PDF + queue job      │ ask: embed question,
                                        ▼                                    ▼  retrieve top-k chunks,
                                   PostgreSQL + pgvector  <────────────  stream Gemini's answer (SSE)
                                        ▲
                                        │ claim job, extract pages (PyMuPDF), chunk, embed (Gemini), store vectors
                                   docqa-worker
                                        │
                                        └──> OpenTelemetry Collector (OTLP, traces + metrics)
```

- **Ingestion is asynchronous.** `POST /api/documents` stores the PDF and a job row in one
  transaction and returns `202`. The worker claims jobs with `FOR UPDATE SKIP LOCKED`, sends a
  heartbeat per batch, and a reaper re-queues jobs whose worker died.
- **Chunks never cross pages**, so every retrieved passage carries an exact page number that the
  model cites inline as `[p. N]` and the UI turns into a tooltip with the source excerpt.
- **RAG versus sending the whole PDF.** Gemini accepts whole PDFs directly (up to about 1000
  pages). For one document per question that is simpler. RAG earns its place when documents
  exceed the context, when questions span a library of documents, or when re-sending a large
  document on every question is too slow or expensive.

## Repository layout

| Path | What |
|---|---|
| `app/` | Python service: API (`docqa-api`), worker (`docqa-worker`), migrations (`docqa-migrate`), tests, Dockerfile |
| `k8s/base`, `k8s/overlays/{dev,prod}` | Kustomize manifests: Postgres StatefulSet, migration Job (Argo PreSync hook), API, worker, Istio Gateway/VirtualService/AuthorizationPolicies, NetworkPolicies |
| `istio/` | Istio 1.31 (sidecar mode) from the upstream Helm charts via kustomize, with the MicroShift CNI bootstrap |
| `observability/` | OpenTelemetry Collector (OTLP in, Prometheus exposition + debug out) |
| `argocd/` | Argo CD install and the four Applications: `istio`, `observability`, `docqa-dev` (automated), `docqa-prod` (manual) |
| `jenkins/` | Jenkins controller image (Podman remote client) and Configuration as Code |
| `ansible/` | Playbook that bootstraps the cluster side and the Jenkins container, and creates the app Secrets from environment variables |
| `Jenkinsfile` | Checkout → Test (pytest in a container, JUnit report) → Build (`podman build`) → Scan (Trivy, fails on fixable CRITICAL) → Push → bump the dev overlay |

## Running locally

```
cp .env.example .env && $EDITOR .env   # GOOGLE_API_KEY from https://aistudio.google.com (free tier)
podman compose up --build
open http://localhost:8090
```

Unit tests run against the locked dependency set, in Jenkins inside a Python container
(`agent { docker { ... } }`) and locally with [uv](https://docs.astral.sh/uv/):

```
cd app && uv sync --extra test && uv run pytest
```

## Deploying

Prerequisites: an OpenShift or MicroShift cluster in the current kubeconfig context, rootless
Podman for the Jenkins container, Ansible with the `kubernetes.core`, `containers.podman` and
`community.crypto` collections.

```
export GOOGLE_API_KEY=... DOCQA_API_TOKEN=... DOCQA_POSTGRES_PASSWORD=...
cp jenkins/.env.example jenkins/.env && $EDITOR jenkins/.env
cd ansible && ansible-galaxy collection install -r requirements.yml && ansible-playbook playbook.yml
```

The playbook installs Argo CD, writes the Secrets, registers the Applications and runs
Jenkins as a rootless Podman container that builds through the host's Podman API socket. Argo CD then installs Istio and the collector and deploys dev. Prod is deployed by
pressing Sync in Argo CD. Rerunning the playbook is idempotent.

Secrets never live in git: the playbook reads them from the environment and writes
`docqa-secrets` and `docqa-postgres` into each namespace. In a larger installation these
would come from Vault or the External Secrets Operator instead.

## Security model

- Every pod runs under OpenShift's `restricted-v2` SCC: arbitrary UID, no capabilities,
  read-only root filesystem, seccomp `RuntimeDefault`.
- Istio enforces STRICT mTLS mesh-wide. `AuthorizationPolicy` allows only the ingress gateway to
  reach the API, only the API, worker and migration job to reach Postgres, and only docqa
  workloads to push telemetry. NetworkPolicies add a second layer the CNI enforces regardless
  of sidecars.
- Trivy blocks the pipeline on fixable CRITICAL findings. The image applies Debian security
  updates at build time and pins a patched `anyio`.
- Every API call must carry `Authorization: Bearer $DOCQA_API_TOKEN`; the UI asks for it once
  and keeps it in the browser. Per-user identity (OIDC at the gateway) is the next step.

## Configuration

All settings come from the environment (`DOCQA_*`, see `app/docqa/config.py`). Notable ones:

| Variable | Default | Purpose |
|---|---|---|
| `DOCQA_LLM_MODEL` | `gemini-3.6-flash` | Answering model |
| `DOCQA_EMBEDDING_MODEL` | `gemini-embedding-2` | Embedding model; `DOCQA_EMBEDDING_DIM` (1536) must match the schema, so changing either means a new migration |
| `DOCQA_TOP_K` | `8` | Passages retrieved per question |
| `DOCQA_CHUNK_SIZE` / `DOCQA_CHUNK_OVERLAP` | `1200` / `150` | Characters per chunk |
| `DOCQA_MAX_UPLOAD_MB` | `200` | Upload limit |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | unset | Where traces and metrics go; unset disables export |

## Platform notes

- **Rootless Podman.** Jenkins runs as a rootless Podman container with `userns=keep-id`, so
  the `jenkins` user inside is your user outside and can use the Podman API socket and a
  bind-mounted home at the same path on both sides, which the Docker Pipeline plugin needs for
  per-stage containers. Images are referenced with their registry (`docker.io/...`) because
  Podman does not resolve short names. `podman compose` needs `compose_providers =
  ["podman-compose"]` in `~/.config/containers/containers.conf` when Docker Desktop's compose
  is also on the PATH. Testing the image with an OpenShift-style UID (`--user 1000680000:0`)
  only works with Docker or root Podman; rootless Podman can map UIDs only within your
  `/etc/subuid` range.

- **Istio on MicroShift.** MicroShift has no Multus and CRI-O loads CNI plugins only from
  `/run/cni/bin`. istio-cni is installed in chained mode into a `.conflist` that a bootstrap
  init container derives from the OVN-Kubernetes config, keeping OVN's network name and CNI
  spec version. Without that, istio-cni's own conversion renames the network and CRI-O stops
  creating pods.
- **Native sidecars** (`ENABLE_NATIVE_SIDECARS`) let the migration Job complete and start the
  proxy before application containers.
- **Argo CD renders Helm through kustomize** (`kustomize.buildOptions: --enable-helm`), so the
  Istio install is plain GitOps with pinned chart versions and values in git.
- **Sync waves** order istiod before the ingress gateway, whose image is filled in by istiod's
  injection webhook.
